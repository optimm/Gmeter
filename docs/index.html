Load testing for HTTP and gRPC, written in Go

Gmeter sends requests at the rate you set and reports latency percentiles, throughput and errors. It can ramp through a load profile, find the highest rate your service holds under an SLO, replay real traffic, compare two runs in CI, and spread one test across machines. One binary, no scripts to write.

brew install optimm/tap/gmeter
Or with Go 1.26 or newer: go install github.com/optimm/Gmeter/cmd/gmeter@latest

897µs or 505.2ms
Same run, different clock

Both numbers are the p90 of the same test: one timed from when each request was sent, the other from when it was due. Most load testers only show you the first. Gmeter keeps sending on schedule through a stall and times every request from the moment it was due, so the stall lands in your p99 instead of vanishing.

The requests a stall delays are the ones most testers never send

Most load testers send a request, wait for the reply, then send the next. When the server freezes, they freeze with it. The requests real users would have sent during that second are never sent, so they are never measured, and the percentiles come out looking healthy. This is called coordinated omission.

Gmeter schedules request n at start + n / rate and never waits for the server to decide. A request that goes out late, because the server or Gmeter itself was busy, is still timed from when it was due. Both numbers are in every report, side by side, so you can see how much of the latency came from the stall.

Six commands, one honest clock

Run at a rate, a step test or a ramp

Constant rate, -stages for steps and ramps, Poisson arrivals with a seed you can replay. The report has corrected and service latency, a per-second timeline that puts a time on every spike, a breakdown of where each request's time went, and a line where Gmeter checks its own timing.

$ gmeter -rate 200 -duration 5s -workers 20 http://127.0.0.1:18080/
requests   1000 scheduled   1000 ok   0 bad status   0 failed   0 dropped
achieved   200.1 rps (target 200) over 5.00s
generator  timer lag p99 1.1ms, max 14.3ms   late 163 (16.3%)

latency, corrected (from each request's intended send time)

Find the most it can take within your target

Give it a latency target and an error budget. It doubles the rate until a trial misses, bisects, then re-runs the answer to see whether it holds. It also tells you when the answer needs a caveat, and when the limit it hit was Gmeter's rather than the server's.

$ gmeter find -slo p99=50ms -trial 5s -warmup 1s http://127.0.0.1:18082/
   #  phase         rate        p99  errors  result
   1  grow           100      8.2ms    0.0%  pass
   2  grow           200      7.7ms    0.0%  pass
   3  grow           400      9.1ms    0.0%  pass
   4  grow           800    183.1ms    0.0%  FAIL  p99 is 183.1ms, over the 50ms target
   5  bisect         600     12.7ms    0.0%  pass
   6  bisect         700     26.8ms    0.0%  pass
   7  bisect         750     52.9ms    0.0%  FAIL  p99 is 52.9ms, over the 50ms target
   8  bisect         725     34.5ms    0.0%  pass
   9  confirm        725     39.1ms    0.0%  pass
  10  confirm        725     38.8ms    0.0%  pass

result  the highest rate meeting p99 ≤ 50ms is about 725 rps
        held in 2 of 2 re-runs at 725 rps

How the search works and how far to trust it

Replay production traffic, bursts included

Feed it an nginx or Apache access log, or JSON Lines, and it sends each request when it was recorded, with the real mix of endpoints. Results come per endpoint. It sends only GET and HEAD unless you say otherwise, so a log full of DELETEs can't change your staging data by accident.

# a 10-second trace at about 300 rps, against a server with four slots
endpoints, busiest first (corrected latency)
  endpoint             scheduled     bad  failed       p50       p99       max
  GET /orders/:id           1961       0       0     4.3ms    72.9ms    89.0ms
  GET /search                625       0       0    42.6ms   105.3ms   118.9ms
  GET /users/:id/cart        459       0       0     4.3ms    70.6ms    80.5ms

The same 4,000 requests at 400 a second on average gave a p99 of 5.4ms when evenly spaced and 121.1ms at their recorded pace, because the bursts queue. An average rate hides that.

Trace formats, pacing and safety

Compare two runs, and fail the build on a regression

Every run can be saved with its full latency histograms. diff compares two runs from those histograms, warns when the runs weren't set up the same way, and with -threshold exits 1 when p99 grew too much.

$ gmeter diff -threshold 20 before.json after.json
                            A            B    change
achieved rps            200.1        200.1     +0.0%
latency, corrected
  p50                   442µs        572µs    +29.3%
  p99                   3.0ms      951.6ms +31966.3%

share of B's requests that are slower than A's percentiles
  slower than A's p99 (3.0ms): 21.8%   (at most 1.0% if nothing changed)

The last line is something two percentiles can't tell you: how many more of your requests got slow.

Errors, phases and per-endpoint gates

gRPC on the same clock

Call any unary method by name. The schema comes from server reflection or a descriptor set, so there's no code to generate. The request is checked against the method's input type before anything is sent, and the results are counted by status code.

$ gmeter grpc -plaintext -call gmeter.demo.Echo/Say \
    -data '{"name":"ann","delay_ms":5}' -rate 1000 -duration 10s 127.0.0.1:18097
requests   10000 scheduled   10000 ok   0 bad status   0 failed   0 dropped
achieved   999.4 rps (target 1000) over 10.01s
codes      OK: 10000

Flags, status codes and what it doesn't do

More load than one machine can send

When the generator runs out of CPU, its requests go out late and the report blames the server. Gmeter warns you when that happens. To fix it, run gmeter agent on a few machines and give the controller -agents. The agents send back full histograms and the controller adds them up, so the merged p99 is the p99 of every request, never an average of p99s.

$ export GMETER_TOKEN='a long random password'
$ gmeter -agents gen1:7070,gen2:7070,gen3:7070,gen4:7070 -rate 40000 -duration 10s -workers 64 http://target/

# measured on one 10-core Mac: 40,000 rps for 10s, two runs where two are given
generator                    achieved      corrected p99   late
one CPU                      33,265 rps    2.00s, 2.02s    100%
four agents, one CPU each    39,998 rps    579µs, 4.4ms    0.6%, 1.0%
no CPU limit (reference)     39,992 rps    364µs           0.5%

When to use something else

  • Multi-step user journeys with logins, state and think time: k6 or Locust.
  • Streaming gRPC methods: k6 or ghz.
  • A browser in the loop: k6's browser module or Playwright.
  • A hosted dashboard for a team to share: Grafana Cloud k6 or Locust's web UI.

Under the hood

Never averages percentiles
Every result keeps its full log-linear histogram: about 250KB, with at most 0.1% error at any size. Stages, windows and agents are combined by adding histograms together.
No drift over millions of requests
Request n's due time is computed from n, never by adding up intervals, so rounding errors can't accumulate. A generator that falls behind catches up, and each late request keeps its due time.
Precise timing, at a small CPU cost
The scheduler sleeps, then busy-waits the last 200µs. At 100 rps that brought the corrected p50 from 2.4ms down to 601µs, against a service p50 of 541µs. The busy-wait is capped at a quarter of a core and turns itself off above about 5,000 rps.
Recording without locks
Each worker records into its own atomic histogram, padded to a 128-byte cache line, and a sampler reads them. With 8 goroutines recording at once, padding took a record from 2.0–3.1ns down to 0.92ns.
Two dependencies, both pinned
Everything is Go's standard library except gRPC support, which pins grpc v1.85.0 and protobuf v1.36.12.
Safe by default
Replays send only GET and HEAD unless you say otherwise. Agents listen on localhost unless told otherwise, and read their password from an environment variable, never a flag. Passwords in URLs are redacted everywhere they're printed or saved.
